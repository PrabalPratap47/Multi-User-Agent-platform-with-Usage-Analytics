# Database

| | |
|---|---|
| Database | SQLite (a single file, no server, no credentials) |
| ORM | Prisma 6 (`prisma` / `@prisma/client` 6.19.x) |
| Schema | `backend/prisma/schema.prisma` |
| Migrations | `backend/prisma/migrations/` |
| Development database | `backend/data/dev.db` (`backend/.env.local`) |
| Test database | `backend/data/test.db` (`backend/.env.test`) |

## Configuration

```env
# backend/.env.local
DATABASE_URL="file:../data/dev.db"

# backend/.env.test
DATABASE_URL="file:../data/test.db"
```

Relative SQLite paths are resolved against the directory that holds
`schema.prisma` (`backend/prisma/`), so `file:../data/dev.db` is
`backend/data/dev.db`. `src/db/sqlitePath.ts` resolves the URL the same way
for the running app, and `src/db/client.ts` hands Prisma the absolute path, so
the CLI and the app always use the same file.

The `.db` files (and SQLite `-journal`/`-wal`/`-shm` side files) are
git-ignored; `backend/data/.gitkeep` keeps the folder in the repository.

## Data model

11 models. Every `id` is an autoincrementing integer except `AgentRun.id` (a
UUID string generated by Prisma). Every model has `createdAt` (or an
equivalent timestamp) defaulting to the insert time; `User.updatedAt` is
maintained by Prisma.

| Model (table) | Purpose | Key relations | Unique |
|---|---|---|---|
| `User` (`users`) | Accounts; `role` is the `Role` enum (`ADMIN`, `USER`) | owns every per-user table (cascade delete) | `email` |
| `RefreshToken` (`refresh_tokens`) | Server-side sessions (SHA-256 token hashes) | `user` (cascade) | `tokenHash` |
| `Agent` (`agents`) | Registered agents | runs, logs, results (cascade) | `name` |
| `AgentRun` (`agent_runs`) | One row per agent invocation; `status` is `RunStatus` (`PENDING`, `RUNNING`, `SUCCESS`, `ERROR`); optional `batchId`, `cvDocumentId` and a safe `errorMessage` | `user`, `agent` (cascade), `cvDocument` (set null) | - |
| `LlmUsageLog` (`llm_usage_logs`) | One row per LLM call, actual provider token counts; `status` is `LogStatus`; `providerResponseId` is the provider's response id; `isSeedData` marks demo rows | `run` (set null), `user`, `agent` (cascade) | - |
| `CvDocument` (`cv_documents`) | Uploaded CV text, optional `batchId` | `user` (cascade) | - |
| `CvRecommendation` (`cv_recommendations`) | Immutable agent output for a CV | `cvDocument`, `user`, `agent` (cascade), `run` (set null) | `runId` |
| `RecommendationDecision` (`recommendation_decisions`) | Append-only ACCEPT/MODIFY/REJECT decision (`DecisionType`) | `recommendation`, `cvDocument`, `user` (cascade), `run` (set null) | - |
| `SentimentResult` (`sentiment_results`) | Sentiment agent output (`Sentiment` enum) | `user`, `agent` (cascade), `run` (set null) | `runId` |
| `ExternalAgentLog` (`external_agent_logs`) | One imported log file | `user` (cascade) | - |
| `ExternalAgentLogRecord` (`external_agent_log_records`) | One validated imported record; never mixed into internal analytics | `import` (cascade) | - |

The baseline migration contains 25 `@@index` indexes (including the
descending `createdAt`/`timestamp` ones), the 5 unique indexes, 20 foreign
keys and 7 CHECK constraints (5 enum, 2 business rules). The two later
migrations add 2 indexes and 1 foreign key, so the current schema has 27
`@@index` indexes, 5 unique indexes, 21 foreign keys and the same 7 CHECK
constraints.

## SQLite-specific details

These are the only places where the schema differs from the previous
PostgreSQL version. No model, relation, index or unique constraint was
removed.

| Feature | PostgreSQL version | SQLite version | Effect |
|---|---|---|---|
| Enums (`Role`, `RunStatus`, `LogStatus`, `DecisionType`, `Sentiment`) | Native `CREATE TYPE ... AS ENUM` | Prisma enum stored as `TEXT`, plus a hand-written `CHECK (col IN (...))` per column | Same TypeScript types; invalid values rejected by Prisma and by the database |
| `Json` fields (`confidenceScores`, `rationale`, `rawResponse`, `parseErrors`, `rawRecord`) | `JSONB` | Prisma `Json` (stored as text) | Same API. Not used for JSON-path filtering anywhere. |
| `CvRecommendation.secondaryCategories`, `RecommendationDecision.finalSecondaryCategories` | `TEXT[]` | `Json` holding a `string[]` | SQLite has no list columns. Writes pass the array unchanged; reads go through `src/utils/categoryList.ts`, which validates with Zod and throws on anything that is not a string array. API responses keep the same array shape. |
| Business-rule CHECKs | Added with `ALTER TABLE ... ADD CONSTRAINT`, using `btrim()` | Inline in `CREATE TABLE`, using `trim()` | Same rules: a decision reason is required unless ACCEPT; REJECT has no final category, ACCEPT/MODIFY must have one |
| `Float` / `DateTime` / `Boolean` | `DOUBLE PRECISION` / `TIMESTAMP(3)` / `BOOLEAN` | `REAL` / `DATETIME` / `BOOLEAN` | No behavior change |
| Foreign keys | Enforced | Enforced (Prisma enables SQLite foreign keys); same `CASCADE` / `SET NULL` rules | No behavior change |

### Things to know

- **Hand-written CHECK constraints.** Prisma's schema language can't express
  CHECK constraints. They live only in
  `prisma/migrations/20261007000000_init_sqlite/migration.sql` (marked
  `-- hand-written`). When a future `prisma migrate dev` alters one of those
  tables, Prisma rebuilds the table in SQLite and does **not** carry the
  CHECKs over. Review every generated migration that touches `users`,
  `agent_runs`, `llm_usage_logs`, `recommendation_decisions` or
  `sentiment_results`, and add the constraints back. The two later
  migrations below were therefore written by hand as `ALTER TABLE ... ADD
  COLUMN`, which keeps the existing tables and their CHECKs.
- **One writer at a time.** SQLite serializes writes. Batch CV processing
  runs up to 3 classifications per batch concurrently (see
  BATCH_CV_PROCESSING.md), and several users' batches can run at once, so
  writes can wait on the write lock. This is fine for local and academic use. A multi-user
  production deployment should move back to a server database.
- **Case sensitivity.** Equality and unique checks are case-sensitive, as
  they were in PostgreSQL. The code uses no `contains`/`LIKE` filters, so
  SQLite's case-insensitive `LIKE` does not affect anything.

## Migration history

| Folder | Status |
|---|---|
| `prisma/migrations/20261007000000_init_sqlite/` | **Active.** SQLite baseline (the schema as of 2026-10-07), plus the CHECK constraints. Generated with `prisma migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma --script`. |
| `prisma/migrations/20261008000000_agent_run_cv_document_link/` | **Active.** Adds `agent_runs.cvDocumentId` (FK to `cv_documents`, `ON DELETE SET NULL`, indexed) and `agent_runs.errorMessage`, so batch status can report each file's state and failure reason. Hand-written `ADD COLUMN`. |
| `prisma/migrations/20261008120000_usage_log_provider_response_id/` | **Active.** Adds `llm_usage_logs.providerResponseId` (indexed), so every usage row can be matched to exactly one raw provider response. Hand-written `ADD COLUMN`. |
| `prisma/migrations_postgresql_archive/` | **Archived, never applied.** The five PostgreSQL migrations (2026-10-06) that built the same schema step by step. They use PostgreSQL-only SQL (`CREATE TYPE`, `SERIAL`, `JSONB`, `TEXT[]`, `ALTER COLUMN TYPE`, `UPDATE ... FROM`, `btrim`) and cannot run on SQLite. Kept for reference only. Prisma reads only `prisma/migrations/`. |

There was no PostgreSQL data to carry over (no PostgreSQL server was ever set
up for this project), so the baseline starts from an empty database. A fresh
clone gets the full schema from `npm run db:setup` (development) and
`npm test` / `npm run db:reset:test` (testing). A development database
created before the later migrations is brought up to date with
`npm run db:migrate:deploy`. To check first, run
`npx dotenv -e .env.local -- prisma migrate status` from `backend/`. It lists
unapplied migrations and exits with code 1 while any are pending.

### Startup migration check

`src/server.ts` runs `checkMigrations` (`src/db/migrationCheck.ts`) **before**
run recovery and before it listens.

**What it compares.** The migration folders in `prisma/migrations/` (each folder
with a `migration.sql`) against Prisma's history table `_prisma_migrations`, read
through the runtime client. This is the comparison `prisma migrate status` makes.
The check is read-only and never applies migrations. It doesn't need the Prisma
CLI, which is a dev dependency and so missing from a production install.

**When the server refuses to start** (exit code 1, `Refusing to start: …` plus a
`DATABASE_SCHEMA_CHECK_FAILED` log event):

| State | Reason | Message tells the operator to |
|---|---|---|
| A checked-in migration has no finished, not-rolled-back history row | `PENDING` | Back up, then `cd backend && npm run db:migrate:deploy` (`db:migrate:test` for the test database) |
| The database file is missing, or has no `_prisma_migrations` table | `NOT_INITIALIZED` | `cd backend && npm run db:setup` (`db:reset:test` for tests). A missing file is detected **without connecting**, so no empty file is created. |
| A history row with neither `finished_at` nor `rolled_back_at` | `FAILED` | Fix it first (Prisma `migrate resolve`) |
| An applied migration that has no folder here | `UNKNOWN_APPLIED` | Use code that matches the database |
| The migrations folder is unreadable or empty, or the history can't be queried | `UNVERIFIABLE` | Fail closed; check that `DATABASE_URL` is a readable SQLite file |

**Safety of the message.** It names the database by its path under `backend/` (e.g.
`data/dev.db`), or by file name otherwise, never by the connection string. On a
read error it shows only the Prisma error code.

**What it doesn't check:**
- migration checksums: an edited, already-applied `migration.sql` isn't detected,
  and line-ending changes on Windows would cause false alarms;
- schema drift made outside migrations, such as manual `ALTER TABLE`;
- databases used by the verification scripts (`verify:*`, `eval:*`). Those import
  `app.ts` directly and migrate their own throwaway databases.

## Seed data

`npm run db:seed` (development database only) deletes all rows and creates:

- 4 demo users: `admin@example.com` (`ADMIN`), `user1`, `user2`, `user3@example.com` (`USER`), all with password `password123`, for local development only.
- The 2 agent registrations (CV Classification Agent, Sentiment Analysis Agent).
- A few demo pipeline records (3 agent runs, 2 CV recommendations with decisions, a sentiment result) with their usage logs. Every demo usage log has `isSeedData = true`. Only `llm_usage_logs` carries that flag, so `analyticsService.ts` identifies the demo **runs** through their flagged usage log and excludes the logs, those runs, their recommendations and the decisions on them from every metric. Dashboards therefore count only real, application-generated activity (see docs/ANALYTICS_API.md).

The test suite never uses the seed; each test file creates and removes its own fixtures.
